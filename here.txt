● I traced the full cold-launch and warm-launch paths: runThisOnWindows.vbs → launcher.py → bootstrap.py → mcu_flash_gui.py. Here is what's slowing it down and what to do about it,

  Why it feels slow

  The first window users see is the "Setup" window. On a warm launch where env already exists, the visible flow is roughly:

  1. runThisOnWindows.vbs calls PurgePythonCache over the entire project (recursively). With env\Lib\site-packages and src\libs deep inside the project, that walks tens of thousands 
  of files on every launch.
  2. launcher.py then calls the same purge in Python (purge_python_cache) before doing anything else.
  3. bootstrap.py does it a third time at module import. Three independent walks of the same tree on every launch.
  4. bootstrap.py builds a Tk window and a custom font set; on Windows loading Montserrat TTFs and creating a Tk root is ~300–500ms of UI-thread time before any background work      
  starts.
  5. _run_setup_in_thread runs, in order: ensure_python_system_environment (registry writes), then unconditionally re-activates the venv (probes python -c "import sys"), then calls  
  run_update_checks(auto_update=False).
  6. run_update_checks is the real culprit on warm launches. It fans out ~9 concurrent network checks (PyPI JSON, GitHub releases/redirect, winget search, pip show per package,      
  arduino-cli version, pio --version, arduino-cli upgrade fallback). Each has an 8–20s timeout, runs in parallel — but only after the user has already been staring at the spinner for
  several seconds waiting for the project selector to appear.
  7. After all that, mcu_flash_gui.py is spawned as a fresh process and re-imports bootstrap (the first lines do from bootstrap import …), which itself re-runs DPI awareness,        
  file-attribute pokes, etc.
  8. Inside MCUUploadGUI.__init__, load_gui_config() reads a JSON file every call (it has a 2s in-memory cache, so that's fine), then _build_ui() constructs every widget before the  
  window is ever deiconified. The Project Selector dialog then runs synchronously on the same thread; on large last_sketch_dir trees the directory walk blocks the main thread for a  
  noticeable moment.

  So the user-perceived delay is essentially: 3 full project tree walks → 1 cold-start Tk window → 9 concurrent network requests → 1 extra Python process import → 1 more Tk window   
  build → Project Selector — for what is conceptually "open my IDE."

  Big wins (do these first)
